# 修仙记事本 · 使用教程

> 这份教程讲三件事：**这游戏是怎么设计的**、**代码有哪些规矩**、**怎么带着 AI 继续往下做**。
> 读完你应该能回答一个问题：为什么这个仓库改内容基本不用碰引擎——以及怎样保住这个优点。

---

## 第一章 · 设计思路

### 1.1 这游戏到底在卖什么体验

《修仙记事本》的核心不是"修仙"，是"**记事**"。玩家看到的不是数值面板，而是一条一年一行往下流的日志：测灵根、领功法、攒灵石、被师兄抢功劳、娘从村里捎来口信……玩法的全部载体就是这条日志流。

所以设计的一切取舍都围绕一个问题：**这条流水账，读起来像不像一个凡人修士的一生。**

什么叫"像"？我们定的基调叫**凡人流**，三个特征：

- **资源算计**：灵石永远不够，买东西要掂量，借钱要还；
- **境界压迫**：头上永远有更高的境界，60 岁筑不了基就是死；
- **人情冷暖**：有人骗你，有人报恩，有人抢你功劳，旧友结丹了捎来四个字"等你上来"。

写事件文案之前，先问自己：这条事件放进一个凡人的一生里，违和吗？

### 1.2 三根设计支柱

**支柱一：内容和引擎彻底分开。**

打开 `assets/data.js`，你会发现里面没有任何"逻辑"——全是数据：事件、机缘、图鉴、结局。引擎在 `assets/loop.js` 里，它不认识任何一条具体事件，只认识"字段"。

这是全项目最重要的一条架构决策，好处有两个：

1. **写内容的人（或 AI）不需要懂引擎**。加一条新事件 = 在数组里加一个对象，改错顶多这条事件不触发，不会搞崩游戏；
2. **AI 协作成本极低**。把 Schema 和文案规范贴给 AI，它就能批量产出合格事件——这就是第三章 vibecoding 能成立的原因。

反过来，这意味着一条铁律：**任何"某个事件如何如何"的特判代码都不许进引擎。** 引擎只许认识字段，不许认识事件 id。

**支柱二：机制藏在引擎里，露出的是故事。**

举筑基期的"丹药耐药性"为例。机制上它是一套计数器：凝元丹吃到第 6 枚药效减半，第 11 枚触底并触发丹毒抉择。但玩家全程看不到任何"耐药值：6/10"——他看到的只是某年日志里一句"药效，似乎不如从前了"，再往后是一个"停药清修还是硬扛"的抉择。

原则：**如果一个机制需要在 UI 上加一块面板向玩家解释，那它多半超标了。** 好机制是自己从文案里长出来的。

**支柱三：随机性优先，不做明牌。**

如果一个抉择是"选项 A 明显比 B 好"，那它不是抉择，是阅读理解题。所以本项目的抉择绝大多数用 `outcomes` 加权随机：选"趁妖兽熟睡取宝"，七成拿到宝物，三成被掀出洞府——玩家赌的是概率，不是背答案。

这也让同一局游戏每次玩都不一样：189 条（v1）→ 320 条（v2）事件 + 加权随机 + 剧情链分支，重玩性是这么来的，不是靠内容总量硬堆。

### 1.3 节奏是怎么控的

一年的日志由"槽位"决定放什么类型的事件，比例大致是：

| 槽位 | 占比 | 作用 |
| --- | --- | --- |
| daily 常规 | ~65% | 填充年度：修炼、坊市、宗门日常 |
| chance 机遇 | ~15% | 给甜头：捡漏、遇贵人 |
| trib 劫难 | ~12% | 给压力：伤病、破财、仇家 |
| miracle 奇遇 | ~5% | 大转折：洞天、灵兽、秘境入口 |
| flavor 留白 | ~3% | 什么都不发生的年份——"山中无历日，桃花开第三回" |

注意最后一行。**留白是刻意设计的**：一年什么事都没发生，反而是凡人流最有味道的年份。别让事件密度拉满，满则腻。

另外两条节奏保险丝：

- **一年 1/2/3 件事 = 50%/35%/15%**，防止某年刷屏某年空白；
- **连续 4 年没有抉择 → 第 5 年强制塞一个**，防止玩家变成纯看戏的。

### 1.4 数值设计的思路：先定"感觉"，再倒推数字

数值不是算出来的，是**先定体验目标再倒推**的。以境界为例：

- 体验目标："资质中等的人，40 岁左右筑基"——于是倒推出炼气 13 层共需 650 修为、基础增速 `6 + 灵根/6 + 悟性/8 + 功法×2`；
- 体验目标："资质差的要有真实的大限恐惧"——于是 60 岁未筑基强制坐化结局，寿元按《凡人修仙传》的设定（炼气一百二、筑基两三百）取；
- 体验目标："结丹要难到让人犹豫要不要赌"——于是筑基到结丹约需 45–79 年，结丹时年龄落在 90–130 岁，而筑基寿元 250——慢资质的玩家会在"再攒攒"和"赌一把"之间真实纠结。

**改数值之前先跑模拟器**：`node tools/sim.js` 会批量跑虚拟人生，告诉你筑基年龄分布、存活率、事件触发频率。拍脑袋调一个数，可能把整条节奏链带崩。

经济系统同理，核心机制叫**按需商人**：你缺钱，钱庄掌柜来问你要不要借贷；你缺筑基丹，丹贩子来敲门；你没功法，游方道人路过。实现上就是触发条件 `cond.invMax`（持有量**低于**某值才触发）。这样既解了玩家卡关的死局，又顺手写了人情冷暖——雪中送炭的人，总是另有所图。

### 1.5 剧情链的"续与断"

剧情链（`chain` 字段）是让几年、几十年跨度的事件串成故事的机制。v2 开放筑基/结丹时，11 条老链做了一次盘点，决策逻辑很能说明凡人流的审美：

- **人际链续**：仇家筑基后登门了断、道侣筑基或坐化、徒弟下山闯荡又回来——人是跟着你一辈子的；
- **资源链断**：炼气期借的钱、遇到的骗子、想家的念头，全断在炼气——**仙凡两隔**。你筑基了，那些凡俗旧事就真的过去了。

最狠的一条：道侣坐化（`daolv_4b`）。它不设"救回来"的选项，只有"TA 替你理了理衣领，笑着说先走一步"。凡人流的刀，不给你翻盘的机会。

### 1.6 秘境：把"冒险"做成可控的结构

秘境是 v2 的主玩法，结构是三段式：

1. **传闻**：坊市流言埋下伏笔（"据说城西有古修士坐化之地"）；
2. **入口**：一扇门，进不进随你；
3. **分层探索**：连续几屏点选，越深奖励越狠、风险越大，每个节点都给你"撤离"的退路。

关键设计：**结丹三宝只产自深处**。想要好东西就得往深处走，往深处走就可能死在里面——贪与怕的拉锯就是秘境的乐趣。而且掉率刻意调成"有人就是集不齐三宝"——集不齐怎么办？攒钱买结金丹，或者硬闯。条条路都能走，只是代价不同。这也是凡人流。

### 1.7 审核红线也是设计约束

这游戏首发于平台活动，有几条硬措辞约束，现在已沉淀为项目文案规范（不只是为了过审，也符合修仙题材的语感）：

- 禁词：一世、前世、来世、轮回、投胎、享年、重生；
- 死亡只写：坐化、兵解、道消；
- 成熟内容必须带 `minAge`。

## 第二章 · 代码规范

### 2.1 文件职责：谁管什么

```
index.html        三视图骨架：开局 → 修行(流年日志) → 结局卡；无逻辑
assets/data.js    ★ 全部内容：机缘/事件/秘境/结局/图鉴 —— 纯数据，零逻辑
assets/core.js    状态 S、属性/背包/存档等基础操作
assets/loop.js    年度循环：事件抽取(eligible)、触发(fireEvent)、结算
assets/ui.js      视图渲染：日志、背包、进度条
assets/pop.js     弹窗交互：抉择/拍卖/火候/秘境/图鉴
assets/style.css  水墨风样式
tools/            lint.js(校验) / sim.js(模拟) / dgtest.js(秘境诊断) / 打包.py
```

规矩只有一条：**data.js 里不许出现逻辑，其他文件里不许出现具体事件。** 拿不准一段代码放哪，就用这条量。

### 2.2 事件 Schema：每个字段是什么意思

一条事件长这样（真实示例精简）：

```js
{ id: "zb_lingtian_1", type: "daily", cat: "ziyuan", realms: [1], cooldown: 5,
  cond: { notFlag: "散修" },
  text: "你名下的半亩灵田遭了虫灾。管事问：请灵植夫除虫要二十灵石，还是自己下田？",
  choices: [
    { text: "请灵植夫", sub: "灵石 -20，田保住了", cond: { inv: { "灵石": 20 } },
      result: "灵植夫三天除了虫。秋后灵谷收成不错，卖出五十五灵石。",
      effect: { inv: { "灵石": 35 } } },
    { text: "自己下田", sub: "省是省，累", outcomes: [
      { weight: 7, result: "……虫除了，腰也快断了。", effect: { inv: { "灵石": 55 }, attrs: { "根骨": -2 } } },
      { weight: 3, result: "……误伤了灵根苗。", effect: { inv: { "灵石": 15 } } }
    ] }
  ] }
```

逐字段解释：

| 字段 | 含义 | 要点 |
| --- | --- | --- |
| `id` | 唯一标识 | 前缀表境界：炼气无前缀、`zb_` 筑基、`jd_` 结丹、`mj_<id>_in` 秘境入口、`mjw_<id>` 秘境传闻。**id 一旦发布永不改名**（它存在玩家的存档里） |
| `type` | 年份槽位 | `daily/chance/trib/miracle/flavor`，决定它在一年里以什么角色出现（见 §1.3） |
| `cat` | 内容分类 | `xiulian/ziyuan/zhandou/renji/xinjing/jiyuan`，用于财侣法地配比统计 |
| `realms` | 生效境界 | `[0]`炼气 `[1]`筑基 `[2]`结丹，可组合如 `[0,1,2]`；炼气老事件用 `layers: [最低层, 最高层]` |
| `minAge` | 经历年数下限 | 显示年龄 = 经历年数 + 12。成熟内容必加 |
| `cooldown` | 触发后 N 年内不再出现 | 可复用事件建议 4–8 年，防复读 |
| `chain` | 剧情链 | `"链id_序号"`，需前序已触发才会出现；同环双变体共用一个 chain id |
| `weight` | 抽取权重 | 默认 1；路线事件引擎自动 ×2.5，不用你管 |
| `cond` | 触发条件 | 见下表 |
| `effect` | 固定结算 | 属性/物品/flag 增减 |
| `choices` | 抉择 | 有 choices 就是弹窗事件 |
| `outcomes` | 加权随机结果 | 替代固定 `result`，权重建议 7:3 或 6:3:1 |
| `auction` / `timing` / `dungeon` | 特殊玩法 | 拍卖 / 火候 / 秘境入口，照现有例子抄 |
| `highlight` | 记入结局名场面 | 只给真正的关键节点用 |

`cond` 条件全家桶（可任意组合）：

```js
cond: {
  min: { "灵根": 60 },        // 属性下限
  max: { "气运": 30 },        // 属性上限
  flag: "宗门", notFlag: "散修",        // 有/无某 flag（还有 flag2/notFlag2）
  inv: { "灵石": 60 },        // 至少持有（花大钱选项的门）
  invMax: { "灵石": 30 },     // 至多持有（"缺什么来什么"商人的门）
  gongfa: 1,                  // 功法等级
  artifact: { "法器": 1 },    // 持有法宝
  combatMin: 120              // 战力门槛
}
```

`effect` 结算全家桶：

```js
effect: {
  attrs: { "根骨": -5 },      // 属性增减（引擎自动 clamp 到 0–120）
  inv: { "灵石": 60 },        // 物品增减（灵石自动 clamp 到 ≥0）
  flag: "洞天",               // 立 flag
  gongfa: 1,                  // 功法升阶
  artifact: { "法器": 1 }     // 给一件具名法宝（自动从名字池取名入背包）
}
```

### 2.3 写事件的六条军规（PR 按此评审）

1. **每个 choice 事件至少留一个不带 cond 的兜底选项**。所有选项都被条件滤掉时，玩家会面对一个啥都点不了的弹窗。
2. **大额扣灵石的选项必须 `cond.inv` 门控**。买不起的选项直接不显示，而不是点了再告诉他钱不够。
3. **抉择优先 `outcomes` 加权随机**，不写"固定哪个好"的明牌选项。
4. **文案过一遍禁词表**（见 §1.7），死亡只写坐化/兵解/道消。
5. **写"事"不写"情"**。情绪从事件和数字里长出来，不用形容词硬灌。对照 `tools/文案规范.md` 里的好例子/反例。
6. **结丹三宝（玄冰魄/炎髓晶/雷灵枝）只许秘境产出**，普通事件不许发——它是逼玩家下秘境的胡萝卜，滥发就废了。

写完跑 `node tools/lint.js`，**必须 0 错误**（它会查 schema、链完整性、禁词、兜底选项、断句句式）。仓库的 git pre-commit 钩子也会自动跑它。

### 2.4 flag 系统与词汇表

游戏没有"任务系统"，一切剧情状态都是 flag（字符串）。常用词汇表在 `tools/文案规范.md` 里，**新增 flag 前先查表，有现成的就别造新词**——比如"道侣坐化"已经存在，你再写个"道侣亡故"，两个体系就永远对不上。

同样，物品名（`inv` 的 key）也是固定词表：灵石、聚气丹、筑基丹、符咒、凝元丹、结金丹。新增物品要先在引擎的丹药槽位登记，不能只在事件里写。

### 2.5 存档兼容：只增不删

存档在玩家浏览器的 localStorage 里，key 是 `xiuxian_save_v1`。三条承诺：

1. **字段只增不删**——旧档缺新字段时一律 `||0` / `||{}` 读默认值；
2. **版本号 `v:1` 不变**——变了旧档就读不出来了；
3. **事件 id 永不改名复用**——玩家存档里记着 `used: ["zb_xxx", …]`。

为什么这样？因为这个游戏的玩家会隔几个月回来续玩，一次不兼容，他几十年的修行就没了。**存档兼容是这个项目的第一公民。**

### 2.6 边界处理的习惯

引擎里有一批已经趟过雷的边界处理，新代码照着做：

- 属性 clamp 到 0–120，灵石 clamp 到 ≥0——但**大额扣款靠 `cond.inv` 门控，不靠 clamp 兜底**（clamp 兜底 = 玩家点了买不起的选项却没破产，逻辑就乱了）；
- 突破成功率一律 `Math.min(0.95, …)` 封顶——永远留 5% 的天意；
- **剧情关键物品（结金丹、三宝）获得时无视背包格限**——不能让玩家因为包满丢剧情物品；普通法宝仍受 12 格限制；
- 日志 DOM 最多保留最近 300 条——200 年人生上千条节点，手机会卡；
- 秘境内死亡：先关弹窗再走死亡流程，防弹窗悬尸。

## 第三章 · 如何继续 vibecoding

先说句实话：**没人读文档，也没人读代码。** 把仓库丢给 AI、说一句"加十条筑基期事件"，才是现实中会发生的事。前两章你大概率也是跳着看的——没关系，它们本来就不是给人背的，是给 AI 查的。

所以这个项目的设计思路是：**规矩不写在"教人怎么教 AI"的教程里，而是写在 AI 工具会自动加载的文件里**，绕过"人转述"这个必然失真、必然被跳过的环节。

### 3.1 你只需要做两件事

**第一件：说人话。**

打开你的 AI 编程工具（Cursor / Copilot / Claude Code / 随便什么），把仓库给它，然后用平时说话的方式提需求：

> "给筑基期加 5 条坊市淘宝的事件，要有赌有亏"
> "魔窟秘境再加一层，里面关着可以放的俘虏"
> "凝元丹太贵了，调到 35"

**不用**贴 Schema，**不用**贴文案规范，**不用**解释什么叫凡人流——仓库根目录的 `AGENTS.md` 是 AI 工具会自动读取的守则文件，规矩全在里面：先拉分支、事件怎么写、禁词是什么、三宝不许乱发、提交前必须过 lint。AI 开工前自己会读。

**第二件：玩一遍。**

AI 干完活会自己跑 lint（`AGENTS.md` 里强制了），但 lint 只能保证"没写错"，保证不了"好玩"。浏览器打开 `index.html` 玩几分钟：新事件出不出来？文案读着出不出戏？满意了，合并分支；不满意，让它改，或者整个分支丢掉重来——它是在分支上干的活，`main` 永远是干净的。

就这两件。方向你把关，手感你把关，剩下的都是 AI 和 lint 的事。

### 3.2 为什么敢这么放手

三个保险丝，层层兜底：

1. **`AGENTS.md` 管行为**：分支、Schema、禁词、数值档位、存档兼容，全写死成 MUST/NEVER，AI 工具启动自动加载；
2. **lint 管对错**：schema 不完整、链断了、用了禁词、没留兜底选项——`node tools/lint.js` 全拦，仓库的 pre-commit 钩子也会拦，想提交都提交不上去；
3. **分支管损失**：就算前两道都漏了，最坏结果是一个分支不好玩，删掉即可。

所以"vibecoding 会不会把项目搞乱"这个问题，答案是：乱不到 main 上。

### 3.3 出问题了找谁

| 症状 | 原因 | 怎么办 |
| --- | --- | --- |
| AI 写出 AI 腔文案 | 它没读 `tools/文案规范.md` | 回一句"按 tools/文案规范.md 的语感重写" |
| AI 在 main 上直接改了 | 工具没自动读 AGENTS.md（少数） | 手动把 `AGENTS.md` 拖进对话一次，以后就会了 |
| 事件加了但游戏里不出现 | 触发条件太苛刻 | 让它自查 cond/realms，或跑 `node tools/sim.js` 看触发频率 |
| lint 报错看不懂 | — | 把报错原样贴给 AI，让它修到 0 错误 |

### 3.4 给维护者的两句提醒
